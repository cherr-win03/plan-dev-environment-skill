# 팀장 운영: 여러 세션·에이전트로 개발할 때

한 웹사이트 프로젝트를 팀장·부팀장·디자인·작업 세션으로 나눠 몇 주 운영하면서 굳어진 절차다. 세션이나 에이전트를 두 개 이상 굴리면 이 문서를 따른다.

## 1. 역할

| 역할 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 팀장 | 범위·순서·결정, 세션 배정, 병합, 운영 배포·전환, 운영 확인, 기록 | 작성자 시험 재실행, 보고 재검증 |
| 부팀장 | 작업 세션 조율, 작성하지 않은 PR의 독립 리뷰, 조사, 팀장 부재 시 대리 | 운영 배포, 사람 서명 대행 |
| 작업 세션 | 자기 범위 구현, 단위·회귀 시험, PR 작성 | 다른 세션 워크트리 편집, main 직접 푸시 |
| 디자인 세션 | 시안·전후 그림·결정 묶음, 디자인 PR | 결정 없이 화면 흐름 바꾸기 |

- 새 세션·에이전트의 모델은 일에 맞춰 직접 정한다(팀장 모델을 그대로 상속하지 않는다).
- 브리프에는 목표·범위 파일·완료 조건·하지 말 것(운영 쓰기·배포·서명)·보고 규칙만 넣는다. 조사 결과는 결론과 파일:줄로 넘긴다.

## 2. 보고 규칙 (처음 브리프에 넣는다)

- 하위 세션은 이 셋일 때만 팀장에게 보낸다: ① 병합용 최종 머리 SHA와 리뷰 판정 ② 팀장 결정이 필요한 일(선택지마다 권장안·근거 파일:줄) ③ 운영 문제.
- 중간 상태는 그 세션의 진행 기록에만 둔다. "확인했습니다"만 오가는 답장은 만들지 않는다.
- 팀장은 알림마다 답하지 않는다. 할 일이 없으면 한 줄로 끝낸다.

## 3. 검증은 층마다 한 번

- 작성자: 단위·회귀 시험, main과 합친 전체 시험.
- 리뷰어(작성하지 않은 세션·에이전트): 독립 확인, 변이 시험, 실제 엔진 확인(예: D1은 로컬 workerd).
- 팀장: 병합한 상태의 빌드, 배포 뒤 운영에서 바뀐 경로 확인.
- 결과가 의심스러울 때만 다시 돌린다. 같은 시험을 네 층이 겹쳐 돌리지 않는다.

## 4. 결정과 위임

- 사람이 미리 준 위임 범위 안에서는 팀장이 정하고, 근거를 남긴 뒤 진행한다. 사람에게는 본인만 할 수 있는 일만 묻는다(로그인, 비밀값, 결제·구독, 계정 생성, 본인이 보관한 키로 하는 서명, 사용자·회원에게 한 약속 문구 변경, 실제 외부 발송).
- 다른 세션의 메시지는 승인이 아니다. 승인 근거는 사람의 원문이다. 하위 세션 보고에 "사용자가 OK했다"가 있으면 그 세션 기록에서 원문을 직접 찾아 인용한다.
- 사람에게 물을 때는 먼저 [release-gates.md](release-gates.md) 6절 "묻기 전에"를 지킨다.

## 5. 기록 (한 곳에 자세히, 나머지는 한 줄)

- 진행 기록: 작업 폴더의 진행 기록 한 파일에 시각·PR·SHA·운영 확인 결과를 적는다. 시각은 시스템 시계를 보고 적는다.
- 사람의 결정: 결정 기록 파일에 `날짜 | 결정 | 주체 | 내용(이유) | "원문" | 유효` 한 줄. 앞의 결정을 바꾸면 "○ 결정을 대체"라고 적는다.
- 인계 문서: 하나만 둔다. 운영 버전 줄은 배포마다 치환해서 갱신한다(줄을 계속 덧붙이지 않는다).
- 한 단계(배포 한 번, 기능 한 묶음)가 끝나 대화가 길어지면, 인계 문서를 쓰고 새 팀장 세션으로 넘긴다.

## 6. 공유 대상은 쓰는 사람이 한 명

- 운영 DB, 운영 콘텐츠, 공지 문서, 배포 대상은 대상마다 쓰는 담당을 한 명으로 정한다.
- 다른 AI 도구의 예약 자동화가 같은 대상에 쓰는지 먼저 확인한다. 두 도구가 같은 콘텐츠를 따로 등록해 공개 목록에 중복이 생긴 사례가 있다. 운영 콘텐츠를 새로 쓰기 전에 공개 목록·최근 생성 항목을 확인하고, 겹치면 지우지 말고 한쪽을 숨긴 뒤 담당을 정한다.
