# 계획서 필수 칸, 구현·검증·리뷰 규칙

유명 개발 스킬 5종(pstack·Ponytail·Superpowers·gstack·spec-kit) 비교에서 가져온 아이디어를 내 말로 옮겼다(설치하지 않고 아이디어만 참고, 문구 복사 없음).

## 0. 규모별로 가볍게

| 규모 | 기준(대략) | 하는 것 |
|---|---|---|
| 작음 | 파일 1~2개, 공개 경로·데이터 구조 안 바뀜 | 필요성 사다리, 시험 1회, 리뷰는 자기 diff 확인 |
| 중간 | 파일 3~7개 또는 새 화면·API 하나 | 아래 계획서 필수 칸 요약판, 작성하지 않은 리뷰어 1회 |
| 큼·운영 전환 | 파일 8개 이상, 새 서비스·표 2개 이상, 운영 설정·스키마·권한 변경 | 계획서 전체, 설계안 2개, 독립 리뷰, [release-gates.md](release-gates.md) 전체 |

큰 계획은 먼저 "더 작게 나눌 수 없나"를 묻는다(복잡도 경보).

## 1. 필요성 사다리 (계획 전, 처음 맞는 칸에서 멈춘다)

1. 꼭 필요한가(요구가 정당화하지 않는 부분은 빼거나 사용자 목표로 다시 확인).
2. 이 저장소·내 템플릿에 이미 있는가.
3. 플랫폼·표준 라이브러리 기능으로 되는가.
4. 이미 설치된 의존성으로 되는가.
5. 가져다 쓸 참고 사례가 있는가. 찾는 순서: 내 자산(내 프로젝트 템플릿, 이전 저장소, 검증해 둔 스킬 목록의 고정 사본) → 공개 자료(공식 예제·스타터, 널리 쓰이는 오픈소스, 공개 스킬·플러그인) → 비슷한 서비스의 구조·흐름(구조만 참고, 코드·문구·이미지 복제 금지). 도입 전 라이선스·유지 상태·보안·이 PC 호환을 보고, 설치·실행할 것은 외부 도구 검증(출처·라이선스·보안·실행 요소 판정)을 먼저 거쳐 버전·커밋을 고정한다. 보류한 자료도 쓸 만하면 검증 메모로 남긴다.
6. 그래도 없으면 최소한으로 새로 쓴다.

검증·보안·접근성·데이터 손실 방지·사용자가 요청한 것은 사다리로 줄이지 않는다.

## 2. 요구 확인

- 첫 단계에서 목표와 "가장 작은 변경"을 자기 말로 한두 줄 적는다.
- 실행해 보면 알 수 있는 사실(어느 방식이 빠른가, API가 무엇을 돌려주는가)은 사람에게 묻지 않고 작은 시제품·실험으로 정한다. 사람에게는 제품·취향·정책 결정만 묻는다.
- 꼭 물을 것은 한 번에 최대 5개, 선택지는 추천안을 먼저, 각 질문에 "왜 중요한지" 한 줄.

## 3. 계획서 필수 칸

- 목표와 가장 작은 변경, 하지 않을 것.
- 데이터 모양: 새로 생기거나 바뀌는 표·JSON·상태의 이름과 필드.
- 구조가 바뀌는 변경이면 서로 다른 설계안 2개와 고른 이유.
- 프로젝트 고정 규칙 점검: AGENTS.md·운영 규칙·보안 규칙·사용자 우선순위(예: 처음 쓰는 사람도 쉽게)를 어기지 않는지. 어기면 이유를 적거나 계획을 바꾼다.
- 작업 단위: 한 번의 리뷰로 판정할 수 있는 가장 작은 크기. 각 작업에 정확한 파일 경로, 다른 작업과 주고받는 인터페이스(함수·API 모양), 완료 조건, 병렬 가능 표시 `[P]`.
- 시험이 다루지 않는 실패 유형(최대 5개)과 그것을 막을 시험을 어느 작업에 넣는지.
- 참고한 것 / 쓰기로 한 것(고정 버전) / 버린 것과 이유.
- 0단계 환경 준비, 마지막 병합·배포 관문, 사용자 몫(로그인·서명·결제 등).
- "미정"으로만 채운 칸을 남기지 않는다.

## 4. 구현

- 이미 워크트리 안인지 먼저 확인한다(`git rev-parse --git-dir`와 `--git-common-dir`가 다르면 워크트리). main/기본 브랜치에서 바로 구현을 시작하지 않는다.
- 버그는 실패하는 재현(시험이나 재현 스크립트)을 먼저 만들고 실패를 확인한다. 가능하면 재현을 수정보다 먼저 커밋한다. 고친 뒤 같은 경로로 통과를 확인한다.
- 분기·반복·파서·돈·권한·보안이 걸린 새 로직에는 작은 시험을 남긴다. 사소한 변경까지 전수 시험을 요구하지는 않는다.
- 일부러 단순하게 처리한 곳(지름길)은 "한계, 다시 볼 조건"을 진행 기록이나 인계 문서에 남긴다.

## 5. 완료라고 말하기 전

- 이번 작업에서 새로 돌린 명령의 출력과 종료 코드만 근거로 쓴다. 예전 결과, "통과할 것", 린트 통과만으로는 완료가 아니다.
- 시험이 0건 실행됐으면 통과가 아니라 미검증이다.
- 하위 에이전트·세션의 "성공" 보고는 diff와 머리 SHA로 확인한다(시험을 다시 돌리는 것은 의심될 때만).
- 새 회귀 시험은 수정을 잠깐 되돌렸을 때 실패하는지 한 번 확인한다.
- 시험 관문 무결성: 시험 기대값 약화, 타임아웃 늘리기, 스냅샷 갱신, 경고 억제 주석은 자동으로 하지 않는다. 필요하면 이유와 함께 팀장 결정으로 기록한다.

## 6. 리뷰 브리프 (리뷰어에게 그대로 준다)

- 판정 두 가지: ① 요구·계획 충족 ② 코드 품질. 둘 다 통과해야 병합 가능.
- 치명 항목 먼저: 데이터 안전·손실, 동시성·경쟁 조건, 권한·신뢰 경계(외부 입력, LLM 출력 포함), 열거값·분기 누락, 시험 관문 약화. 그다음 나머지.
- 바뀐 파일만이 아니라 호출부·피호출부까지 읽는다.
- 지적마다 구체적 사례(어떤 입력·상황 → 어떤 잘못된 결과)가 있어야 한다. 사례가 없으면 지적이 아니다.
- 형식: 번호, 무엇·문제·고칠 방법·안 고치면, 등급 Must/Should/Nice, 마지막에 판정.
- 리뷰어는 코드를 고치지 않는다.
- 같은 작업의 수정 왕복이 3번을 넘으면 작성자를 바꾸거나 한 단계 위 모델로 올리고, 구조 자체를 다시 본다.
- 권한·보안 경계를 바꾸는 변경은 다른 회사 모델(예: Claude 작업이면 Codex CLI)의 교차 검토를 고려한다.
- 리뷰를 받는 쪽은 맞장구치지 않는다. 틀린 지적은 근거(파일:줄, 실행 결과)로 반박하고, 불명확한 지적은 고치기 전에 먼저 묻는다.

## 7. 멈출 때와 기록

- 멈추고 결정을 받는 일: 되돌리기 어려운 동작, 보안, 외부 부작용(발송·게시·결제·운영 쓰기), 계획 붕괴. 위임이 있으면 팀장이 정한다.
- 나머지는 스스로 판정하고 진행 기록에 `판정: 무엇을, 왜` 한 줄을 남긴다. 마지막 보고에 내린 판정을 모아 적는다.
- 대화가 압축된 뒤에는 진행 기록부터 읽고, 끝난 작업을 다시 돌리지 않는다.
- 배포 뒤에는 정한 시간 동안 오류 로그와 핵심 경로를 한 번 더 본다.
- 같은 실수가 두 번 나면 문서 규칙을 늘리지 말고 스크립트·시험·린트로 막는다(예: D1 로컬 실행 점검 스크립트).
