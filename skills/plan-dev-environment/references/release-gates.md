# 병합·배포·운영 전환 관문

개발 계획에 "병합·배포" 단계가 있으면 계획서에 이 관문을 그대로 넣는다. 보안·SEO·접근성 같은 출시 직전 점검표는 따로 두면 좋다.

## 1. 병합 관문

- 작성하지 않은 리뷰어의 판정이 있다(must-fix 0). 리뷰 뒤 커밋이 바뀌었으면 그 머리 SHA로 다시 판정받는다.
- 머리 SHA를 고정해 병합한다: `gh pr merge N --merge --match-head-commit <SHA> --subject "Merge PR #N: <제목>" --body-file <파일>`. 본문에 리뷰 판정과 근거(사용자 결정이면 원문 인용)를 적는다.
- 쌓인 PR(A ← B ← C)은 맨 위부터 그 base 브랜치로 합치고, 매번 다음 PR의 새 머리를 다시 읽은 뒤, 맨 아래 PR을 마지막에 main으로 병합한다. 병합 전 "맨 아래 머리가 리뷰한 최종 SHA를 포함하는가"를 `git merge-base --is-ancestor`로 확인한다(리베이스했다면 `git patch-id`로 같은 변경인지 본다).
- 데이터·콘텐츠 표를 바꾸는 PR(설정 표, 콘텐츠 목록)은 병합 전에 표의 id가 운영의 실제 id와 같은지 대조한다.

## 2. DB 질의는 실제 엔진으로

- 시험용 SQLite·메모리 어댑터는 운영 DB의 제한을 적용하지 않는다. 예: Cloudflare D1은 compound SELECT 5항, 함수 인자 32, 바인딩 100, 문장 100KB, LIKE 패턴 50바이트, 열 100 제한이 있다.
- SQL을 새로 쓰거나 크게 바꾸면 배포 전에 운영 엔진의 로컬판(D1이면 `wrangler d1 execute <DB> --local --file <질의>.sql`)으로 실제 실행한다. 단위 시험 수천 건을 통과한 질의가 운영에서 503을 낸 사례가 있다.

## 3. 배포 절차 (저장소마다 한 번 정해 인계 문서에 둔다)

1. 배포 전용 체크아웃에서 `git fetch` → `git checkout --detach origin/main`. 작업 워크트리에서 배포하지 않는다.
2. 빌드 → 오프라인 설정 점검 → dry-run → 실제 배포.
3. 배포된 설정 일치 확인 → `version.json` 같은 곳의 커밋 값이 방금 병합한 SHA인지 확인.
4. 운영에서 이번에 바뀐 경로를 직접 확인한다(HTTP 상태, 응답 내용, 파일 해시). "배포 성공" 출력만으로 완료라고 하지 않는다.
5. 진행 기록과 인계 문서의 운영 버전 줄을 갱신한다.

- 비밀값 폴더는 경로만 명령에 넘기고 안을 열거나 출력하지 않는다.
- 롤백 기준 커밋을 인계 문서에 둔다. 데이터 구조가 바뀐 지점보다 앞으로는 되돌리지 않는다고 함께 적는다.

## 4. 운영 전환(설정·계약·스키마를 바꾸는 배포)

- 바꾸는 값이 어떤 해시·불변식·서명에 들어가는지 코드로 계산한 뒤 계획한다. 예: 회원 동의가 정책 해시와 정확히 같을 때만 유효하면, 해시에 들어가는 값(한도 등)을 바꾸는 순간 전원 재동의가 생긴다.
- 전환 표를 PR 본문에 둔다: 순서, 각 단계의 사람 서명·승인 여부와 횟수, 잠시 멈추는 API와 예상 시간, 되돌리는 방법, 단계별 확인 방법.
- 위험한 전환 두 개를 같은 날 하지 않는다. 한 번에 묶을 수 있는 전환은 묶어 서명·중단을 줄인다.
- 로컬 리허설에서 사용자에게 보이는 경로까지 확인한다: 기존 사용자 복귀, 작성 중 자료 보존, 관리자 진입, 막힌 동작이 오류 대신 안내로 보이는지.

## 5. 외부 서비스 비용·한도

- 유료 API는 한 화면 열기당 호출 수를 정해 둔다(예: 1회 이하, 전체 목록 0회). 하루 상한을 콘솔에 걸고, 상한에 걸렸을 때 보일 문구를 만든다.
- 청구 등급(SKU)이 의도한 것인지 콘솔에서 확인한다. 개발 중 반복 열기로 상한을 태우지 않는다.
- 무료 등급의 자동 정지(예: 일정 기간 미사용 시 일시중지되는 DB·인증 서비스)를 인계 문서에 적는다.
- 구독·결제·약관 동의는 사람이 한다. 필요한 시점과 이유만 미리 알린다.

## 6. 사용자에게 묻기 전에

- 선택지의 전제를 코드로 확인한다. 확인 안 한 전제로 권장안을 냈다가 뒤집혀 다시 묻게 되는 일이 생긴다. 전제가 틀린 것을 알면 바로 정정하고 다시 묻는다.
- 같은 결정이 이미 기록(결정 기록 파일·결정 문서·다른 세션)에 있는지 먼저 본다.
- 선택지마다 사용자가 체감하는 결과, 서명·재동의·비용 같은 부담, 권장안을 쉬운 말로 쓴다(질문 형식은 plan-and-verify.md 2절).
- 가입·로그인·동의처럼 흐름 단계를 바꾸는 지시는 "뺄 단계 / 남길 단계"를 확인한 뒤 배포한다.
