# plan-dev-environment — 개발 계획에 맞춘 워크트리와 개발 환경 준비

**핵심: 계획 단계에서는 조사만 하고 "환경 준비"를 구현 계획의 1단계로 넣는다. 계획이 승인되면 그 1단계(워크트리 → 설치 → 기존 테스트·빌드 검증)를 먼저 끝내고 결과를 남긴 뒤 구현으로 넘어간다. 원본 작업 트리의 미커밋 변경·브랜치·인덱스는 건드리지 않는다.**

참고 문서(필요한 것만 읽는다):
- [plan-and-verify.md](references/plan-and-verify.md): 규모별 절차, 필요성 사다리·참고 사례, 계획서 필수 칸, 구현·완료·리뷰·멈춤 기준.
- [release-gates.md](references/release-gates.md): 병합, 실제 DB 엔진, 배포, 운영 전환, 외부 비용, 묻기 전 확인.
- [team-lead.md](references/team-lead.md): 여러 세션·에이전트 운영(역할·보고·검증 층·위임·기록).
- [this-machine.example.md](references/this-machine.example.md), [project.example.md](references/project.example.md): 내 PC 도구·함정, 프로젝트 위치 안내를 적어 두는 양식. 복사해 `this-machine.md`·`project-<이름>.md`로 채운다.

## 언제 어떻게 발동하는가
- 계획 모드에서 개발 의도가 있을 때, 그리고 계획 승인 직후에 쓴다. 문서·행사 계획이나 개념 설명이면 쓰지 않는다.
- **계획 모드에서**: 아래 1절의 조사와, 모드가 허용하는 비변경 검사(읽기·`git status`·기존 테스트/빌드 실행)까지 한다. 설치, 소스 편집, 커밋, 워크트리·세션 생성은 하지 않고 계획의 1단계로 적는다. 관측한 사실과 "실행 단계에서 할 일"을 구분해 쓴다.
- **승인된 실행 단계에서**: 1단계 전체를 수행한다. 이미 승인된 로컬 설치·환경 설정을 단계마다 다시 묻지 않는다. 설치 완료와 검증 완료를 구분해 보고한다.
- 하위 에이전트로 조사·검증을 나눌 때는 일의 난이도에 맞춰 모델을 직접 정한다: 찾기·목록은 가벼운 모델, 설치·검사 실행·문서화는 일반 모델, 설계·원인 분석은 고성능 모델. 메인 모델을 그대로 상속시키지 않는다.

## 1. 프로젝트와 기준 상태 확인 (계획 모드에서 수행)
1. 현재 요청, 최신 계획, 적용되는 `AGENTS.md`·`CLAUDE.md`를 확인한다. 과거 인계 문서는 현재 코드·HEAD와 대조한다. 프로젝트 위치 안내(`references/project-<이름>.md`)가 있으면 거기서 시작한다(위치 안내이지 현재 상태의 증거가 아니다).
2. 대상 앱 폴더와 Git 최상위(`git rev-parse --show-toplevel`), 공통 Git 디렉터리, 모노레포면 실행할 하위 패키지를 기록한다. 상위 공용 작업 폴더 전체를 앱 저장소로 오인하지 않는다.
3. 진입점·소스·서버·DB·테스트·빌드/CI 파일을 찾는다. 실행 방법의 우선 근거: README, 패키지 명세(package.json·pyproject·requirements), 잠금 파일, 런타임 버전 지정(.nvmrc·.python-version·engines), 기존 setup/run 스크립트. 의존성·캐시·빌드 폴더(node_modules, .venv, dist, __pycache__)는 탐색하지 않는다.
4. 원본의 HEAD·브랜치·staged/unstaged/untracked 상태, 기존 워크트리(`git worktree list`), 작업 중인 다른 세션을 확인한다. `.env` 값·운영 DB·자격증명은 어디에도 복사하지 않는다.
5. Git 이력이 없는 새 프로젝트면 워크트리를 만들었다고 보고하지 않는다. 승인 뒤 격리된 새 폴더와 첫 로컬 기준 커밋을 준비하거나 단일 환경으로 시작한다. 공용 상위 폴더 전체를 `git init`/`git add`하지 않는다.
6. 규모를 정하고(작음·중간·큼) 필요성 사다리와 요구 확인을 거친 뒤 계획서 필수 칸을 채운다([plan-and-verify.md](references/plan-and-verify.md) 0~3절). 작은 일은 가볍게 한다.
   계획서에 "0단계: 환경 준비"를 넣는다: 확인한 실행 명령, 빠진 도구·의존성, 워크트리 분담안(필요할 때만), 검증 명령, 예상 실패(외부 설정 누락 등).
7. 새 프로젝트·새 기능이면 확정 전에 참고 사례(내 템플릿·이전 저장소·검증해 둔 스킬 → 공개 예제·오픈소스 → 비슷한 서비스 구조)로 계획을 다듬고, 쓰기로 한 것은 고정 버전으로 0단계 설치 목록에 넣는다([plan-and-verify.md](references/plan-and-verify.md) 1절).
8. 운영 반영이 있으면 마지막 단계로 병합·배포 관문을 넣고, 설정·스키마 변경이면 바뀌는 값이 걸리는 해시·서명·동의를 코드로 계산해 적는다([release-gates.md](references/release-gates.md)).

## 2. 계획에 맞춘 분담과 워크트리 (실행 단계)
- 단일 작업이면 워크트리 하나로 충분하다. 기능 경계·수정 파일·검증 범위가 독립적이고 병렬의 이점이 있을 때만 나눈다. 조사·설명만 하는 역할에는 워크트리를 만들지 않는다. 각 단위에 담당·의존 작업·완료 조건을 적고 통합 담당은 한 명(메인)이다.
- 도구 우선순위: 쓰는 도구에 워크트리 기능(예: Claude Code의 `EnterWorktree`, 세션 시작 시 워크트리, 에이전트 `isolation: "worktree"`)이 있으면 그것을 쓴다. 없거나 실패하면 `git worktree add`로 만들고 그 사실을 기록한다.
- 에이전트의 격리 워크트리는 보통 원격(origin) 기준에서 잘린다. 푸시하지 않은 로컬 커밋 위에서 병렬 작업을 시킬 때는 먼저 푸시하거나, 에이전트에게 `git worktree add -b <브랜치> <경로> <로컬 커밋>`으로 직접 만들게 하고 시작 커밋을 확인시킨다. 공용 체크아웃에서 `git switch`하지 말라고 브리프에 적는다.
- 운영 배포가 있는 저장소는 작업 워크트리와 별도로 배포 전용 체크아웃(origin/main detached)을 둔다.
- 만들기 전에 이미 워크트리 안인지(`git rev-parse --git-dir` ≠ `--git-common-dir`) 확인하고, 저장소 안에 워크트리 폴더를 둘 때는 `git check-ignore`로 무시되는지 확인한다. 기본 브랜치에서 바로 구현을 시작하지 않는다.
- 새 워크트리는 검증한 공통 기준 커밋에서 만든다. 필요한 미커밋 소스가 빠지지 않는지 확인하고, 원본을 stash/reset/checkout하지 않는다. 필요하면 별도 임시 인덱스(`GIT_INDEX_FILE`)로 명시적 파일 목록만 담은 로컬 기준 커밋을 만든다.
- 생성 뒤 실제 경로·기준 커밋·브랜치를 확인한다. 결과가 불명확하면 상태부터 확인해 중복 생성하지 않는다.
- 워크트리로 코드를 나눠도 외부 DB·클라우드 문서·공용 런타임·배포 대상은 공유된다. 같은 외부 자료의 수정·배포는 한 명이 맡는다.

## 3. 설치와 실행 (실행 단계)
- 런타임·패키지 관리자·Git·브라우저·로컬 서비스의 설치 상태와 프로젝트 요구 버전을 비교한다. 내 PC 도구 상태와 반복된 함정은 `references/this-machine.md`에 적어 둔다. 빠진 필수 도구만 공식 경로로 설치하고 무관한 전역 업그레이드는 하지 않는다. 사용자가 입력해야 하는 키·로그인은 요청만 한다.
- 잠금 파일과 프로젝트 방식대로 재현 설치한다: npm은 `npm ci`(잠금 없으면 `npm install`, Windows PowerShell에서는 `npm.cmd`), pnpm은 `--frozen-lockfile`, Python은 프로젝트 전용 `.venv`에 잠금/요구 파일로. 명세·잠금 불일치는 덮어쓰지 말고 원인과 최소 수정 범위를 적는다. 기존 setup 스크립트가 있으면 그것을 쓴다.
- 필요하면 재실행 가능한 setup/run 도우미를 만들어 경로·런타임·설치·실행·검사를 연결하고, 실패 단계와 재실행 명령을 남긴다.
- 워크트리마다 포트·빌드 결과·임시 데이터·로컬 DB를 분리한다. 포트가 사용 중이면 그 서버를 종료하지 말고 충돌을 보고하거나 새 포트를 실행기와 테스트 설정에 함께 적용한다. 로컬 서버는 loopback에 바인딩한다.
- 운영 runtime 설정·공용 DB·로컬 상태 폴더(예: `.wrangler`)는 복제하지 않는다. 로컬 마이그레이션과 합성 fixture로 준비한다. 운영 데이터·외부 발송·유료 리소스·공개 배포는 범위 밖이다.
- 검증이 끝난 시험·브라우저 출력은 무시된 경로만 골라 바로 지운다(`git status --short --ignored`; 추적 파일이 섞인 폴더는 통째로 지우지 않는다). 시험 출력은 금방 수십~수백 GB가 된다.

## 4. 기존 상태 검증과 완료
- 각 구현 워크트리에서 의존성 확인 → 저장소에 정의된 lint/typecheck → 기존 테스트 → 필요한 빌드를 실행한다. 없는 검사를 통과로 쓰지 않고, 과거 결과를 새 결과로 재사용하지 않는다. 첫 실패를 재시도 성공으로 지우지 않는다.
- 운영 DB가 시험 엔진과 다르면(Cloudflare D1·Postgres 등) 운영 엔진의 로컬판으로 DB 점검이 도는지도 이 단계에서 확인한다. 시험용 SQLite만 통과한 것은 DB 검증 완료가 아니다.
- 설치·검사에 필요한 최소 환경 수정만 한다. 발견한 기존 결함은 재현 근거와 함께 환경 수정과 구분해 적고, 승인된 계획에 포함된 것만 그 단계에서 고친다.
- 워크트리를 여러 개 쓰면 대표 두 개의 서버·검사를 겹쳐 실행해 포트·데이터·결과 경로가 분리되는지 확인한다.
- 원본과 재사용한 환경의 변경 상태를 다시 확인해 준비 과정이 사용자 수정·스테이징·브랜치를 건드리지 않았는지 확인한다.
- 결과 문서(프로젝트의 문서 폴더나 팀이 정한 위치)에 적을 것: 앱 경로, 구조·실행 방법, 기준 커밋, 역할별 워크트리 경로·담당·포트, 설치/시작/검사 명령, 실행 시각·종료 코드·검사 건수·로그 위치, 실패/미실행/다음 조치.
- 상태는 셋 중 하나로 선언한다: `검증 완료`(독립 실행과 필수 검사 통과) / `환경 설치 완료, 검증 제한`(이유 명시) / `준비 미완료`. 실패에 직접 의존하는 단계는 보류하고 독립적인 승인 범위는 계속한다. 환경 준비만 요청받았으면 여기서 멈추고, 전체 개발 실행이 승인돼 있으면 확인한 기준 상태 위에서 구현 단계로 이어간다.

## 5. 구현·운영 단계로 이어갈 때
- 구현·완료 선언·리뷰·멈춤 기준은 [plan-and-verify.md](references/plan-and-verify.md) 4~7절, 여러 세션 운영은 [team-lead.md](references/team-lead.md), 병합·배포·전환은 [release-gates.md](references/release-gates.md)를 따른다.
- 완료는 이번에 새로 돌린 결과와 운영에서 바뀐 경로 확인으로만 말한다. 사용자에게 물을 때는 전제를 코드로 먼저 확인하고, 위임받은 범위 안에서는 스스로 정해 기록한다.
